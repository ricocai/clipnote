## 1. 项目背景与目标

### 1.1 一句话定位

一款**鸿蒙优先**的本地笔记应用：自动感知剪贴板内容成记，Markdown 图文呈现，支持整篇/段落 **TTS 朗读**，通过 **MCP 协议**向本机与外部 AI Agent 开放笔记能力，数据**本地优先**、架构预留云同步。

### 1.2 需求清单

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| R1 | 剪贴板自动感知并记入笔记 | P0 | 自动从剪贴板保存为笔记条目，多入口兜底 |
| R2 | 本地存储 | P0 | 数据优先保存在本地，SQLite 为唯一事实源 |
| R3 | Markdown 图文显示 | P0 | 渲染 + 附件图片管理 |
| R4 | HTML 文件显示 | P0 | 应用内展示或调用本地浏览器 |
| R5 | **TTS 朗读** | **P1（本期新增）** | 整篇或选中段落朗读；优先端侧 TTS 大模型，离线可用 |
| R6 | **MCP 协议支持** | **P1（方案刷新）** | 本机 Agent / 外部 Agent / 云端代理三通道开放笔记能力 |
| R7 | 云同步 | P2（预留） | 一期只留接口与数据字段，云端开发由独立任务承接 |
| R8 | 搜索与组织 | P1 | 全文检索（中文）、标签、收藏、时间线 |

### 1.3 非目标（Non-goals）

- 一期**不做**云端同步的实现与账号体系（仅预留）；
- 不做跨平台（Android/iOS）——鸿蒙优先，通过平台抽象层降低未来迁移成本；
- TTS 一期**不做**音色克隆与多情感控制（Kokoro 无克隆能力，属刻意取舍）。

## 2. 总体架构

![总体分层架构](assets/01-architecture.png)

**架构原则**：本地优先 · 隐私默认不出设备 · 分层与接口隔离（可测试）· 渲染/合成/连接三处引擎均可插拔。

- **表现层**：ArkUI 声明式 UI + MVVM；阅读页内嵌「阅读 + 朗读」一体视图（朗读时高亮跟随）。
- **领域服务层**：`SpeechService`（朗读管线，本期新增）、`McpService`（多通道接入，本期重构）与既有服务并列，全部服务无 UI 依赖、可被单测覆盖。
- **数据层**：RelationalStore(SQLite) 唯一事实源 + 附件目录内容寻址；`SyncAdapter` 仅为接口占位。
- **平台抽象层**：`ITtsEngine`、`IAudio`、`INet` 等接口隔离鸿蒙 API 与第三方引擎，Mock 可测。
- **系统能力/端侧推理**：pasteboard、ArkWeb、**sherpa-onnx（TTS 端侧推理）**、AudioRenderer/AVSession、**HMAF 鸿蒙智能体框架**。

**工程结构**（Stage 模型）：单 HAP（entry）+ HAR 共享库 `common`（数据层/工具/解析器）+ HAR `speech`（TTS）+ HAR `mcp`（协议），功能边界清晰、按 HAR 独立演进。

## 4. 核心模块设计

### 4.1 剪贴板采集（R1）

![剪贴板数据流](assets/02-clipboard-flow.png)

要点（与 V1.0 一致，概述）：

- **入口矩阵**：前台监听 `pasteboard.on('change')` → 切前台拉取比对 → 系统分享接收 → 桌面卡片一键存。鸿蒙出于隐私安全**不提供常驻后台剪贴板监听**，以上入口均由前台生命周期或系统级能力触发，共同逼近“复制即记”。
- **管线**：内容读取 → 类型识别与结构化（链接卡片/代码块/表格）→ 敏感内容提示（验证码/密码类特征）→ SHA-256 去重（时间窗）→ **剪贴板收件箱**暂存。
- **转存**：自动规则（来源白名单直接入笔记）或手动一键转存；收件箱可编辑、合并、忽略。
- **权限与隐私**：`ohos.permission.READ_PASTEBOARD`，读取行为对用户可见可关；真机需验证 API 12/13 弹窗与授权行为（风险 R2）。

### 4.2 本地存储与数据模型（R2）

核心表（SQLite，UUID v7 主键、`updated_at`、软删 `deleted_at` 为云同步预留）：

```sql
note(id, title, content_md, content_type, source, origin_hash,
     pinned, created_at, updated_at, deleted_at)
tag(id, name UNIQUE)            note_tag(note_id, tag_id)
attachment(id, note_id, kind, file_path, sha256, mime, size, created_at)
clipboard_item(id, kind, raw_text, structured_json, origin_app,
               sha256, captured_at, state)        -- 收件箱暂存
note_fts(...)                                    -- FTS 外部内容表 + 触发器同步
sync_state(entity, entity_id, local_rev, remote_rev, dirty, synced_at)  -- 仅建表预留
```

- 附件**内容寻址**（`attachments/ab/cd/<sha256>.<ext>`），天然去重；
- 中文全文检索：FTS5 不可用中文分词时，触发器生成 2-gram 索引列兜底；
- 备份导出：全库导出为 MD + 附件目录压缩包（本地优先的自救通道）。

### 4.3 Markdown 编辑与图文渲染（R3）

- **自研 MD→AST 解析器先行**（common HAR）：编辑器、渲染、朗读（§5.6）、剪贴板结构化四处复用，只解析一次；
- **渲染双引擎可插拔**（`IRenderer`）：一期 Web 引擎（ArkWeb + markdown-it + highlight.js，`onInterceptRequest` 拦截映射本地附件虚拟路径）快速交付；二期基于同一 AST 演进 ArkUI 原生渲染器（Text/Image/Span 组件树）；
- 图片粘贴/选择 → 附件目录 → 相对路径引用；
- 编辑器一期 TextArea + 工具条，演进方向富文本编辑。

### 4.4 HTML 展示（R4）

- 应用内：ArkWeb 沙箱加载本地 HTML（JS 可关，来源标记 `notes-html://`）；
- 系统浏览器：`Want` action `ohos.want.action.viewData` 拉起；
- 安全：不加载远程资源默认策略、禁文件域越权访问。

### 4.5 MCP 多通道接入（R6，V1.1 重构）

![MCP 多通道架构](assets/03-mcp-arch.png)

按评审意见，原“双模”设计刷新为**一套 McpService、三条通道**：Tools/Resources/Prompts 一份定义，通道层只负责传输与安全，全部复用。

**方案 A · 设备侧 Server（已定，先行落地）**

| 通道 | 场景 | 传输 | 可行性 |
|---|---|---|---|
| **A1 本机 Agent** | 小艺/系统智能体、第三方端侧 Agent App | **鸿蒙智能体框架 2.0（HMAF）原生支持 MCP 接入**，App 注册 MCP 服务；第三方 Agent 走 127.0.0.1 本地回环 | 高（系统级通道，HDC 2026 已确认 HMAF 支持 Agent/Skill/MCP/A2A） |
| **A2 外部 Agent（局域网）** | PC 上 Claude/Cursor 等 MCP Host | App 内嵌轻量 MCP Server（自研 HTTP/1.1 over socket，兼容 Streamable HTTP），配对码 + Bearer Token + TLS | 高（出站/入站均在用户局域网，前台使用） |

**方案 B · 云端轮询发现 + 直连 MCP 代理（待 PoC 考证）**

流程：① 按既定配置（60~120s 间隔 / 前台即时）轮询云端 Agent 接口，拉取**对端连接信息与一次性 Token** → ② 鉴权与信息校验（签名防篡改、Token 限一次）→ ③ App **主动外连（outbound WSS）对端 MCP 代理**，长连接复用 → ④ 对端无公网地址时，退化为**云端 Relay 中继**转发。

可行性考证结论（回应“具体方案可行性待考证”）：

1. **连接方向**：手机为出站连接，无 NAT 穿透问题——技术可行；前提是对端代理公网可达，否则走中继兜底；
2. **后台限制（最大约束）**：鸿蒙对后台应用冻结网络与长连接。轮询采用**短请求**（单次 <5s）可显著规避，但息屏/挂起状态下定时精度与可达性需真机验证；前台使用场景无此问题；
3. **功耗**：60~120s 心跳级轮询功耗可忽略；实时性由“前台即时轮询 + 本地通知拉起”补齐；
4. **安全**：对端信息签名校验、一次性 Token、双向设备认证、审计日志——防止“云端下发恶意对端地址”的注入风险；
5. **结论**：**技术可行，定位为跨网段/无局域网场景的补充通道**；与方案 A 不互斥。三项假设待 M8 PoC 验证：息屏轮询可达性、直连时延、中继带宽成本。**PoC 未通过则该通道降级为“手动触发同步式”访问。**

能力面（三通道共用）：`create_note / search_notes / get_note / append_to_note / list_tags / delete_note（需用户确认）`；Resources：`notes://`；Prompts：整理收件箱、每日汇总。安全基线：配对码 + Bearer Token、TLS/WSS、敏感操作二次确认、调用审计、默认仅授权设备。

### 4.6 TTS 朗读（R5，V1.1 新增）

![TTS 朗读架构](assets/05-tts-arch.png)

**功能设计**

- **入口**：整篇朗读 / 选中段落（块）朗读 / 剪贴板收件箱试听 / 后台连续播放；
- **朗读管线**（SpeechService，逐段流水线）：MD →AST 提取朗读文本（剔除语法标记，表格/代码块转述或跳过）→ 句子级智能分段（≤300 字，段落边界保读感）→ 文本规范化（数字/日期/缩写/中英混读）→ **流式合成**（`generateAsync` + samples 回调，边合成边播放）；
- **播放层**：环形缓冲平滑播放；语速 0.5~2.0x、音色/音量；段落跳转/重读、**阅读页高亮跟随进度**（AST 段落 id 对齐）；AVSession 支持锁屏/耳机线控；
- **隐私**：合成全程端侧离线，文本不出设备——与“数据优先本地”原则一致。

**端侧 TTS 模型选型（2026-09 调研，高端手机本地部署优先）**

| 模型 | 参数量 | 中文 | 端侧表现 | 协议 | 定位 |
|---|---|---|---|---|---|
| **Kokoro-82M ★推荐** | 82M | 支持 · 8 语种 | CPU 快于实时 · 54 音色（含中文 zf_/zm_ 系列） | Apache 2.0 | **主力引擎** |
| MeloTTS-ZH | ~80M | 支持 · 中英 | CPU 实时 · CER 0.27 · 工业落地多 | MIT | 中文混读备选 |
| KittenTTS | 15~80M | 否 · 仅英文 | 25MB 超小 · CPU | Apache 2.0 | 英文轻量备选 |
| Core Speech Kit | 系统内置 | 支持 | 系统级 · 零集成成本 | 系统 API | 兜底 / 低端机 |

**推荐理由**：Kokoro-82M 在 TTS Arena 开源榜单以 82M 参数压过 10 倍参数模型（质量-体积比第一），Apache 2.0 商用友好，且 **sherpa-onnx 的鸿蒙 HAR 包原生支持 Kokoro 架构**——集成路径最短。**MeloTTS-ZH 作为中英混读场景的 A/B 备选**，系统 TTS 兜底低端机。

**鸿蒙集成要点**：ohpm 引入 `sherpa_onnx` HAR；模型 int8 量化（~85MB）放应用沙箱，**首次使用时下载 + 懒加载**（不入包，控制包体）；Worker 线程执行 `OfflineTts.generateAsync`，samples 回调写入环形缓冲 → AudioRenderer 播放；高端机开启多线程/NPU 加速（sherpa-onnx 支持多 NPU 厂商）。性能预算：旗舰机合成快于实时（朗读 1 分钟文本合成 <1 分钟）。

### 4.7 搜索与组织（R8）

FTS5（或 2-gram 触发器兜底）+ 标签 + 收藏 + 时间线；搜索结果高亮命中片段。与 V1.0 一致，不赘述。

### 4.8 云同步预留（R7）

仅预留：UUID v7 主键、`updated_at`、软删墓碑、`sync_state` 表、`SyncAdapter` 接口。增量同步模型（LWW + 墓碑）、端到端加密选项、后端形态由独立任务《启动项目云端开发（云同步）》（项目内部跟踪）承接，本文档为其提供架构约束输入。

### 4.9 Plan B：小艺插件 + 原生备忘录轻量路线（V1.2 新增）

**提案**：不开发独立 App，只做一个小艺插件（Skill），由小艺感知剪贴板内容并自动保存到鸿蒙原生备忘录，再利用小艺的 Agent 能力对备忘录内容进行整理、消费和分析。

![Plan B 推演](assets/06-plan-b.png)

**逐环节可行性**（E1 已实测 + E2 已完成官方文档查证，2026-09-28）：

| 环节 | 结论 | 依据 |
|---|---|---|
| ① 复制动作 | ✅ 可行 | 用户行为本身 |
| ② 剪贴板感知 | ❌ **不开放（E2 查证结论）** | 「小艺导航条」主动提醒的感知与分发由华为智慧分发服务闭环运营，支持内容类型为**固定清单**（淘/抖/阿里/唯品会/网盘口令、航班号、快递单号、网址、地址、手机号），面向华为合作的头部平台；开发者文档（Intents Kit / 小艺开放平台）中**无第三方按剪贴板内容类型注册服务的通道**。Skill 触发类型（关键词 / LLM 意图 / 正则 / 事件 / 复合）中，"事件触发"公开示例仅定时推送类，**无剪贴板事件源**；Intents Kit 智慧分发的"事件推荐"是应用共享意图数据后由系统提取事件特征（时间/位置），同样与剪贴板无关。**→ Plan B 只能做到半自动（用户对话触发）** |
| ③ 写入备忘录 | ✅ 可行（E1 已亲测闭环） | 真机实测：与小艺对话即可将对话内容写入备忘录。官方通道为小艺 Skill 编排调用备忘录系统 Skill（备忘录已 Skill 化），**比 GUI 模拟人工交互更 native** |
| ④ 数据沉淀 | ❌ **受限（结构性）** | 备忘录无开放 API / 不支持 MCP：数据是黑盒，仅小艺可读。MD 图文渲染、TTS 高亮跟随、全文检索、附件管理、云同步预留——**主线核心能力全部无法实现** |
| ⑤ AI 消费 | ✅ 可行（受制于人） | 小艺可对备忘录内容整理/摘要/分析，但体验完全依赖小艺编排质量，第三方只提供工具片段 |

**结构性限制**（为何只能做备选，不能做主线）：

1. **自动性受限（E2 已证实）**：剪贴板事件入口不向第三方开放，这正是 ClipNote 以独立 App 形态存在的核心理由——App 才有前台 `pasteboard` 监听、分享接收、桌面卡片等完整入口矩阵；
2. **数据黑盒**：沉淀在系统备忘录里的内容第三方无法结构化访问，产品无数据资产、无差异化、难变现；
3. **能力天花板低**：MD 图文、TTS 朗读、MCP 对外开放、云同步预留等全部无法承载。

**正确定位与终局**：E1 + E2 结论收敛后，Plan B 定位明确为**半自动形态的 MVP 价值验证 + 增长入口**——用零开发/轻量 Skill 先验证"复制 → 沉淀 → AI 消费"的用户习惯，跑通后把用户导流到 ClipNote；而 ClipNote 通过 **A1 通道（HMAF · MCP 注册）** 让小艺直接消费其笔记库——**两条路线在 A1 通道合流**：ClipNote 负责采集与资产沉淀，小艺负责智能消费。Plan B 与主线互补而非互斥。

**验证实验进展**：

| 实验 | 状态 | 结论 |
|---|---|---|
| E1 零开发走查 | ✅ **已完成（真机实测）** | 与小艺对话将内容写入备忘录成功，半自动闭环成立，体验可用 |
| E2 触发能力查证 | ✅ **已完成（官方文档查证）** | 导航条主动提醒不开放第三方注册（固定类型清单）；Skill"事件触发"无剪贴板事件源；Intents Kit 智慧分发（习惯/事件/位置推荐、技能调用、本地搜索）入口为小艺对话/搜索/建议，不含剪贴板感知。**全自动路径现阶段不可行** |
