> 评审日期：2026-09-28（北京时间）  
> 评审对象：《技术方案设计.md》V1.3，以及 01—05 共五张架构与路线图  
> 评审性质：设计评审、公开一手资料核验；未执行源码审计、编译、真机测试或上架验证  by ChatGpt
> 结论：**方向可行，建议有条件通过立项；当前版本不宜直接冻结为完整交付基线。先收敛采集承诺，完成关键能力 PoC，再分阶段实施。**

## 1. 核心判断

ClipNote 的价值成立：以本地笔记库承接信息采集、阅读、检索与朗读，再向获授权的 Agent 提供受控访问。原方案的本地优先、领域服务与平台接口隔离、附件内容寻址、保留导出通道等方向值得保留。

主要问题不在 ArkTS 或 SQLite 的选择，而在于**若干尚未验证的系统能力被当作确定前提，同时首期承担了过多独立工程难题**。这些问题会同时影响产品承诺、数据可靠性、隐私边界和排期。

建议作出以下决策：

1. 产品首期承诺改为“用户授权下的前台采集、分享保存与一键粘贴”，不承诺其他 App 内每次复制都自动入库。
2. 本地保存、可信渲染、中文搜索、可恢复导出构成核心闭环；系统离线 TTS 经验证后优先交付。
3. MCP 首先验证一个明确客户端、一个固定协议版本、一个前台局域网通道；HMAF 集成另设平台准入门槛。
4. Kokoro 保留为候选增强引擎。以手机实测决定是否主用，取消“榜单第一”“手机 NPU 可直接开启”等未经充分支持的承诺。
5. 云端轮询与中继退出首期发布关键路径；未来设计为有明确在线状态、身份和数据授权的远程访问功能。

**ClipNote 本体无需实现自治 Agent。**笔记与采集逻辑保持确定性，MCP/意图框架负责暴露受控能力，外部 Agent 负责推理与编排。提供 MCP 工具不等于应用必须内置模型或代理循环。

## 4. 采集能力：可实现的产品承诺是什么

### 4.1 多入口不能等价为全局“复制即记”

**依据：原方案自己已限定“不提供常驻后台剪贴板监听”。**在这个前提下，用户在其他 App 连续复制 A、B、C，再打开 ClipNote，回前台读取最多只能获取届时仍可访问的内容，不能推导出 A、B 都已保存。分享和卡片需要用户动作，也不是复制事件的后台替代物。

| 场景 | 建议承诺 | 必须验证的边界 |
|---|---|---|
| ClipNote 前台且具备读取条件 | 感知变化后进入收件箱 | 变化通知与内容读取权限分别验证；处理重复事件 |
| ClipNote 回到前台 | 检查当前可读内容并提示保存 | 不是历史补采；拒绝授权后不得反复打扰 |
| 用户分享文本、图片或文件 | 接收用户选定内容 | 接收入口、MIME、URI 临时授权与复制时机 |
| 用户点桌面卡片 | 打开采集页面，再完成授权读取或粘贴 | 不能预设卡片执行环境直接拥有剪贴板读取权限 |
| 用户点手动粘贴入口 | 明确操作后读取并预览 | 评估系统粘贴安全控件适配；OpenHarmony 官方说明可作为线索 [S06] |
| 后台、息屏或进程已终止 | 不保证持续采集 | UI 应显示能力边界；不把普通定时器当后台保障 |

**建议替换 §1.1 定位：**

> 一款鸿蒙优先的本地笔记应用：在用户授权与系统允许的运行状态下，通过前台剪贴板采集、分享接收和一键粘贴保存内容；提供 Markdown 图文阅读、离线朗读与受控 Agent 访问，保留可恢复导出与未来同步接口。

### 4.2 收件箱已经属于数据持久化

验证码、口令、密钥即便未进入正式笔记，只要写入 `clipboard_item.raw_text`，就已经被保存。“敏感内容提示”必须说明发生在落盘之前还是之后。

建议默认：先在内存做限长与敏感特征判断；疑似敏感内容不自动持久化，可由用户明确选择保存。普通内容进入收件箱后也要有容量限制、可配置保留期、一键清空，并默认不被 MCP、搜索索引或备份导出包含。检测存在漏判，不能将检测器等同于安全保证。

来源白名单还依赖可靠来源信息。`origin_app` 应允许为空；需要验证其具体 API、权限和可伪造性。剪贴板自带标签与普通字符串不能直接充当可信应用身份。来源不明时不得匹配自动转存白名单。

### 4.3 幂等与内容转换

同一次用户操作可能同时触发分享、前台读取与变化回调。建议以“内容类型 + 规范化版本 + 内容摘要 + 时间窗”合并重复摄取，同时保留用户主动“再次保存”的能力。

代码中的空白、表格中的单元格边界不得被粗暴规范化。URI 图片应在授权有效期内复制到沙箱并核验，不要仅保存外部临时路径。链接卡片默认只保存本地已有标题和 URL；自动抓取网站会产生额外联网与隐私暴露，需另列功能开关。

## 5. MCP：先定义互操作合同，再选择部署形态

### 5.1 协议版本是当前缺失的关键设计输入

本次读取的官方 **2026-07-28** 规范相对 2025-11-25 已发生实质变化：移除协议级会话与初始化握手，增加 `server/discover`，请求携带版本与能力元信息；Streamable HTTP 的 GET 流与部分恢复机制也发生变化。[S01][S02]

因此不能写成“自研轻量 JSON-RPC 2.0，兼容 Streamable HTTP”就视为完成设计，也不能照旧清单强制实现 `initialize` 或 `Mcp-Session-Id` 而不声明版本。

| 事项 | V1.4 应明确的决策 |
|---|---|
| 客户端 | 指定至少一个首发 Host 及实测版本；区分桌面客户端与云端连接器，后者不能当然访问手机局域网地址 |
| 协议 | 优先选择目标客户端已验证支持的正式版本；采用旧版也可以，但必须显式标注 |
| 传输 | 指定 Streamable HTTP 版本；WSS 若使用，应写为自定义隧道或代理内部协议 |
| 能力 | 先实现搜索、读取与必要的建记；Resources/Prompts 按实际客户端需要逐步增加 |
| 兼容 | 发现、请求元信息、错误、取消、列表分页、资源读取分别对照所选版本验收 |
| 扩展 | 应用级审批、幂等键和远程隧道不能被宣传为所有标准 MCP Host 原生支持 |

领域服务和工具 Schema 可以复用，协议适配、安全策略与生命周期仍需按通道分别实现。更合适的结构是 `NoteService + AccessPolicy + McpAdapter + TransportAdapter`。

### 5.2 A1：HMAF 与本机回环必须拆开验收

“HMAF 支持 MCP”即使获得产品层面确认，也不能直接证明以下条件同时成立：

- 任意第三方 App 能在目标最低系统上注册设备侧 MCP Server；
- 小艺通过设备内调用而非云端网关访问笔记；
- App 未运行时能被拉起并获得足够执行时间；
- 该接入方式无需特定资质、审核或合作权限。

原文的 API 12+ 基线与较新的 HMAF 能力之间还缺少版本分层。应分别定义 `minCompatibleVersion`、构建/目标 SDK 与功能可用性检测。A1 不通过时仅关闭系统 Agent 接入，不应影响笔记功能启动。

第三方 App 访问 `127.0.0.1` 是另一条路径，需要验证设备网络隔离和生命周期。**回环地址只限制网络可达范围，不构成调用者身份。**若其他 App 能连接同一端口，也必须鉴权。

### 5.3 A2：局域网可达不等于客户端可用

建议保留“用户主动开启、App 前台使用”的首发边界，但降为待 PoC，而非直接标“高可行”。验证点包括：

1. 手机服务监听地址、Wi-Fi 网络切换、AP 客户端隔离、IPv4/IPv6 与端口占用。
2. HTTPS 证书如何被 Host 信任、证书与地址是否匹配、更新后如何重新建立信任。不能以关闭证书校验作为交付方案。
3. 配对码短时有效、尝试限速；配对后签发每客户端独立的高熵凭证，支持过期、撤销与最小权限。
4. 接口对异常 `Origin` 的检查；同时限制非预期 Host、请求体积、并发与速率。官方传输规范对 Origin 检查有明确要求。[S02]
5. Host 是否支持自定义 Header/Token。配对 Bearer Token 不等于已经实现 MCP 的 HTTP 授权流程；若采用该规范，应按其要求设计发现和授权。[S03]

一期不建议自行解析完整 HTTP/1.1、分块传输、TLS 与长连接。优先评估可维护的成熟实现；若鸿蒙移植成本过高，可把桌面伴随桥作为备选 PoC。桥接会新增桌面端维护和通信成本，不能被视为零成本保底。

### 5.4 B：主动外连解决了连接方向，没有解决后台在线

原文最应删除的是“短请求可显著规避冻结”和“60～120 秒轮询功耗可忽略”。如果进程没有执行机会，请求是 1 秒还是 5 秒都无法启动。轮询成功后的 WSS 仍然依赖同一进程保持运行。

60～120 秒一次，理论上每天约 **720～1,440 次**请求；这是按全天连续运行计算的数量，不是实际系统会执行的数量，也不是耗电测量值。功耗取决于唤醒、无线电状态、网络、重试与握手，必须做空载对照。

建议远程方案调整为：

- 用户主动开启有期限的“远程访问窗口”，客户端能看到在线、离线、授权待确认状态。
- 设备主动连接经批准的网关；远端 Agent 访问网关的标准 MCP 端点，网关通过私有隧道转发到设备。
- 明确定义设备离线、超时、重试、取消和写入幂等。未来若评估推送，只将其作为提醒/可用时唤起路径，不承诺即时执行。
- 网关返回的目标地址必须受域名、端口与设备绑定约束；签名只能证明配置来源，不能保证签名地址本身安全。需防止重定向或地址解析把请求导向未授权目标。
- 若中继能解密正文，应向用户披露；逐段 TLS/WSS 不能自动等同于端到端加密。

这条路径引入设备身份、配对、撤销、服务运维与中继成本。即使不做完整账号体系，也需要信任引导与凭证恢复设计。因此 B 应单独预算并后置，不以 M8 成功作为核心笔记首发条件。

### 5.5 工具级授权比“删除前确认”更重要

读取整本笔记或全库搜索同样可能敏感。外部 Agent 获得内容后，数据已经离开 ClipNote 所控制的设备边界；应用不能再对 Agent 后续上传行为作“零外传”保证。

| 能力 | 建议首发授权语义 |
|---|---|
| `search_notes` | 只搜索已授权集合；限定条数、返回片段长度，默认排除收件箱与回收站 |
| `get_note` | 校验单篇或集合授权；不接受任意本地文件路径 |
| `create_note` | 写入获准集合；校验内容大小与类型；可要求首次授权确认 |
| `append_to_note` | 使用应用级幂等键与预期版本；冲突返回明确结果 |
| `delete_note` | 绑定用户确认的目标 ID 与版本；软删除并可恢复 |
| `list_tags`、Resources | 同样执行授权过滤，避免标签或资源列表泄露未授权信息 |

令牌不得进入 WebView、笔记正文或调试日志；审计优先记客户端、操作、对象 ID、结果与时间，不记录完整正文。笔记中的“请调用工具删除其他内容”等文字是数据，不应扩大服务端权限。工具注解和提示词都不能替代服务端授权检查。

| “约 85MB”就是完整下载体积 | 缺模型清单 | 核算权重、音色、词典、前端数据与压缩包总量 |
| `generateAsync` 加 samples 回调实现流式 | 异步接口名称本身不能证明增量样本交付 | 实测回调粒度、线程、取消和背压；标注句级或样本级 |
| 支持多 NPU 厂商，所以手机可开启 NPU | 推论不成立 | CPU 先行；具体 SoC、执行后端、模型算子支持须单独验证 |
| 系统 TTS “零集成成本” | 表述错误 | 仍有能力检测、音色、初始化、回调、后台与异常处理成本 |

官方鸿蒙 TTS 教程提供 Melo 与 Piper 示例，并采用 `rawfile` 资源路径。[S04] 这支持“有集成基础”，不等于已经证明指定 Kokoro 量化包可以从首次下载后的沙箱路径加载。Melo 也不应因参数量和来源不明的 CER 数字就被判定优劣。

### 6.2 推荐的渐进实现

1. **TTS-0：**先做系统离线引擎 PoC；验证断网、音色可用性、长文与中断，合格后提供整篇与段落朗读。
2. **TTS-1：**通过统一 `ITtsEngine` 接入一个 sherpa-onnx 模型，实测 Kokoro 与 Melo 的代表性样本；首期不同时维护三套完整主力实现。
3. **TTS-2：**有证据后再增加低首包延迟、更多音色与硬件加速。

若系统离线能力不可用，必须显式提示或禁用，不能静默转为在线 TTS 后仍标注“文本不出设备”。首次模型下载是联网取文件，与将笔记文本发往云端应分别说明。

### 6.3 播放时钟、背压与取消必须补充

建议修正管线为：**文档块 → 文本规范化 → 按句及长度上限切分 → 合成 → 有界音频队列 → 播放 → 按实际播放进度高亮**。

图05目前显示“分段 → 流式合成 → 文本规范化”的箭头顺序，应纠正。输入规范化后仍需检查长度，避免数字读法展开后超过模型限制。

- 高亮使用实际已播放位置，不使用“该段已经合成完成”的时间。首期只承诺段落级高亮；逐词同步需要额外对齐数据。
- 合成队列设高低水位，避免整篇预生成导致内存上涨；Native 引擎对象由固定执行上下文持有，按绑定规则传递 PCM 数据。
- 切段、换音色、暂停、停止、来电中断时，废弃旧 generation ID 的样本，防止前一次任务音频继续播放。
- 语速先选模型生成速度或播放层变速的一种；若承诺保音高，需单独验证处理链。
- AVSession 的控制面不等于后台合成资格。合规后台音频任务、AudioRenderer、合成线程、音频焦点与耳机断开均需真机联验。

性能不能只写“RTF < 1”。如果 1× 生成音频在 2× 速度消费时仍沿用同一合成路径，稳定供给可能要求 RTF < 0.5，或需要更大预缓冲。模型内部变速则重新测量，不能直接套用该换算。

## 7. 存储、搜索与渲染

### 7.1 SQLite 是业务元数据权威源，附件仍需恢复协议

“SQLite 唯一事实源”应改为：**业务记录以关系库为权威，附件 blob 由关系库引用并由内容摘要校验；索引与渲染缓存可重建。**图片实际字节并不在当前 SQLite 表中，DB 事务不能自动保护文件写入。

建议拆分附件实体和引用关系：

```text
blob(sha256 PK, relative_path, mime, size, status)
note_attachment(note_id, blob_sha256, role, ordinal)
note(..., revision, content_schema_version)
clipboard_item(..., expires_at, sensitivity, state)
```

这只是逻辑结构建议，不是可直接迁移的 SQL。需进一步定义外键、索引、事务及迁移版本。

附件写入顺序建议：临时写入并验证 → 在同一文件系统内原子改名 → DB 事务提交引用。该方案仍可能留下孤儿文件，因此启动时要有恢复扫描；与之相比，应避免笔记先提交成功却引用不存在的文件。删除先解除引用；垃圾回收经过宽限期，并排除其他笔记、回收站、备份快照仍引用的 blob。

首期补齐：磁盘满、进程被杀、数据库迁移失败、文件丢失、哈希不符、索引重建、共享图片删除后的恢复行为。沙箱隔离不等于静态加密；数据库、附件、导出包和凭证应分别确定保护边界。

### 7.2 导出不是备份恢复的同义词

MD + 附件 ZIP 可用于迁出，但未必保留标签、收藏、来源、时间、HTML 原件、笔记 ID 与附件关系。

建议同时定义：

- **可读导出：**MD/HTML 与附件，重写相对链接，适合其他工具消费。
- **可恢复备份：**包含 `manifest.json`、格式版本、实体元数据、文件摘要与关系，可恢复到空库并得到可核对结果。

备份要有一致性快照或短暂写入协调；不能在附件变化时任意遍历打包。恢复时先校验并暂存，再导入；防止压缩包路径越界、过大解压量与已有 ID 冲突。默认排除设备密钥和 MCP Token，收件箱是否导出需单独明确。

### 7.3 中文搜索要区分三个问题

SQLite FTS5 是扩展能力；默认分词和 trigram 各有匹配边界。[S07] 但上游 SQLite 支持不等于目标 RelationalStore 构建和 API 一定开放同样能力。

1. **FTS5 不可用：**再增加一个 2-gram 文本列不能凭空获得 FTS。应选择普通表倒排索引，或小数据量受限扫描。
2. **FTS5 可用、中文切词不足：**可以在应用层生成分词或 n-gram 后索引，但要定义召回、排序和原文高亮映射。
3. **短查询与特殊文本：**单字查询、混合英文、数字、标点、简繁体、emoji、空格需要单独处理，不能只测两字以上中文。

用同一语料测试 1k/10k 条笔记下的建索引、增量更新、删除过滤、检索延迟与索引膨胀。外部内容 FTS 表还需要验证已有数据回填、触发器和重建流程，不仅是建表成功。

### 7.4 先统一语法入口，再谈统一 AST

自研解析器处理一次，markdown-it 再处理一次，实际仍是双解析；语法不一致会导致屏幕、朗读和导出内容不同。

建议首期选择一个已验证能在目标运行环境使用的成熟解析入口，转换成轻量 `DocumentBlock`：含块类型、源范围、文本、附件引用和文档 revision。渲染与朗读复用块模型。若解析器只能运行在受控 Web 环境，需定义桥接 Schema 与导入解析缓存，不能假定 ArkTS 与浏览器 JS 运行时完全等价。

块 ID 只需在确定的文档 revision 内稳定。编辑后终止旧朗读或重新映射，避免把旧块进度应用到新文档。原生 ArkUI 渲染器保持为后续选项，不在 MVP 预付第二套完整渲染成本。

### 7.5 HTML 与 Markdown 应建立不同信任域

`notes-html://` 名称本身不提供安全隔离。原方案“JS 可关”应改为：导入 HTML 默认禁脚本，原始 HTML 视为不可信内容；用于应用 UI 的可信页面与导入页面隔离。

设计最低要求：

- Markdown 默认不允许执行原始 HTML；如支持子集，做结构清洗与 URL 协议白名单。
- 导入 HTML 限制脚本、事件属性、iframe、表单、重定向、外部字体、CSS URL 和远程图片等入口。
- 文件映射只按授权附件 ID 查找，校验路径规范化结果，拒绝 `..` 与其编码变体，不接受网页传入任意沙箱路径。
- 不向不可信页面暴露原生 JS bridge、凭证、全库 API；应用级脚本与用户文本必须严格分离。
- 默认离线渲染，内容中的图片或样式不能自动联网；测试应观察实际网络请求，不能只检查 JS 开关。
- 外部浏览器打开是数据交接行为：沙箱路径可能不可读，应使用目标平台支持的受控导出/分享机制，验证临时权限与附件路径。

## 8. 云同步预留与 Plan B

### 8.1 预留字段不代表冲突问题已经解决

UUID v7、`updated_at` 与墓碑是有用基础，但设备时钟可能漂移，两个设备可能同时追加，删除也可能与编辑竞争。简单 LWW 会有丢失其中一次修改的风险。

首期不必实现完整 CRDT，但应增加单设备 revision 与修改事务边界，未来同步合同明确：实体稳定身份、并发冲突保存、附件上传依赖、删除传播及墓碑回收。不要把时间戳当唯一因果顺序。墓碑何时可以清理需结合已同步设备和保留策略，不能无限保留也不能无条件短期清理。

目前没有账号与多设备需求时，可以先冻结 `SyncAdapter` 与实体版本合同，避免提前建立将来必须兼容的完整 `sync_state` 表结构。“端到端加密选项”也应保留密钥管理、设备加入与恢复的设计议题，不能理解为后期增加一个布尔开关。

### 8.2 Plan B 的收敛方向正确，证据表述仍需修订

“半自动价值验证 + 潜在增长入口”比全自动插件路线更合理。但四项推论需要收紧：

| 原文推论 | 更准确的表达 |
|---|---|
| 小艺对话写备忘录成功，所以第三方 Skill 可编排该系统能力 | 系统小艺已被作者验证可完成该操作；第三方调用资格与接口另验 |
| 文档没有剪贴板事件源，所以第三方绝不可能实现 | 在已查文档和目标环境中未确认公开可用入口，当前方案不依赖它 |
| 原生备忘录使 MD、TTS、检索等核心能力“全部无法实现” | ClipNote 无法确认获得受控结构化读写；部分体验系统自身可能提供，但产品难以自主保证 |
| 意图共享就是免费增长通道 | 可作为候选分发入口；准入、曝光、转化及迁移路径需验证 |

E1/E2 证据包应包含：机型、系统和小艺版本、账号状态、输入步骤、输出结果、时间、截图/录像、官方文档链接和限制。E3 只验证“用户显式记一下”的需求强度与迁移意愿，不再尝试以未知后台能力支撑核心定位。

**独立 App 的核心理由是可控的数据与体验，而非获得全局后台剪贴板特权。**这一点应在 §4.9 中明确，避免两条路线的自动性差异被夸大。

## 11. 排期复核与建议范围

### 11.1 原排期的准确问题

原 WBS 除 Plan B 外合计 **96 人日**，加入 Plan B 1～2 人日为 **97～98 人日**；“约96”可理解为忽略了该小项，不属于重大算术错误。

真正的问题是人员与日历换算。按每周 5 个工作日、100% 投入的理想条件：

- 1 人：97～98 人日约 **19.4～19.6 周**。
- 2 人：理想均分约 **9.7～9.8 周**，还没有计入串行依赖、返工、休假、审核等待与沟通。

因此“1～2 名研发约10～12周”不能同时成立。日期表也没有给出两人的逐周任务分配。UI/UX 的 8 人日由设计师还是研发承担、M8 的 8 人日是否仅含 PoC、不包含云端生产化，都应写清楚。
