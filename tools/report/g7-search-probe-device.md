### 阅读本报告必须知道的两条口径

1. **真值语义 = 原始字符串子串（LIKE）**。token 型策略（s2/s4）会把查询切词并**丢弃标点**，
   因此含标点查询（如 `，财报`）会命中所有含"财报"的文档——这是**语义差异**（按词检索 vs 按串检索），
   不是实现缺陷。产品必须明确对外宣称哪一种语义。
2. **召回按全量结果集计算，未做 top-N 截断**，避免把"截断"误读为"召回不足"。

## 能力检测

| 能力 | 结果 | 说明 |
|---|---|---|
| FTS5 | 可用 | create virtual table ... using fts5 成功 |
| trigram 分词器 | 可用 | tokenize='trigram' 创建成功（SQLite ≥ 3.34） |

**unicode61 对中文的实际行为**：整段 MATCH '鸿蒙笔记应用' → 1 行；MATCH '笔记' → 0 行；MATCH '笔' → 0 行。（unicode61 把连续 CJK 视为**一个 token**，因此只有整段匹配才命中：查"笔记"命中 0 行即为证据）

## 结论与推荐（供 S3-4 搜索落库采信）

**能力面（对设备成立）**：RelationalStore 所用 OH SQLite 3.40.1 构建**开放 FTS5 且含 trigram 分词器**；unicode61 对连续 CJK 不切词（整段才命中），中文直查不可用。与主机侧 3.51.2 能力结论一致。

**推荐方案：FTS5 trigram（s3）为主路径，LIKE 受限扫描兜底短查询。**

1. ≥3 字符查询（含中文子串、英文、数字、含标点短语）：trigram 召回/精确均 100%（含标点用例精确率也是
   100%，天然按"串"匹配，无需像 s2/s4 那样丢弃标点），无需应用层切词与 gram 表维护；
   万条语料索引体积 8.66 MB（≈正文 2.99 MB 的 2.9 倍），查询 P95 1.401 ms（主机）。
2. 1–2 字符查询：trigram 语义上无法命中（探测实测 0 命中，符合预期），回退 LIKE 受限扫描——
   万条全表扫 P95 2.705 ms（主机），规模可控；随数据增长可再评估。
3. **降级预案**（设备 FTS5 被裁剪的最坏情况，概率低）：普通表 2-gram 倒排（s4），召回 100%，
   但万条体积 39.83 MB（≈正文 13.3 倍）、建索引 1675.91 ms，写入成本显著高于 trigram，仅作预案不进主路径。
4. s2（unicode61+应用层 gram）与 s4 同为 token 语义：含标点查询按词检索（`，财报` 精确率仅 18.6%），
   且索引体积 ≥ trigram、无召回优势，**不推荐**。

**G7 判定：通过。** 设备构建口径下中文检索可行路径明确（trigram + 短查询回退），S3-4 可按此落库。
